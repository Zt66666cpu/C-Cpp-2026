# 架构演进讨论与常见疑惑解答（写作素材沉淀）

本文档记录 `gomoku_ai` 从 V1 线性启发式、V2 双网（MLP NNUE + CNN + Rapfi 外教）向 V3 单网 **Pattern-NNUE + 持久置换表/LMR 搜索** 演进过程中的核心工程决策与关键理论疑惑，可作为课程设计报告与技术博客的一手写作素材。

## 1. 训练监控整合与算力迁移（Mac M 系列 -> Windows RTX 4070）

### 1.1 跨项目统一监控
- 为了在不打断开发流的情况下实时掌握多训练任务的健康度，将五子棋自博弈训练指标（`models/metrics.jsonl`）接入了轻量本地监控面板（`http://127.0.0.1:8766`）与桌面悬浮窗。
- 监控关注的关键指标包括：自博弈单轮耗时（`gen_sec` / `train_sec`）、`NNUE val_mse`、`CNN val_top1`、晋级门控胜率（`vs_heuristic` / `vs_v1` / `vs_prod`）、以及外教对弈战绩（`vs_rapfi`）。

### 1.2 从 Mac CPU/MPS 迁移到 Windows RTX 4070 CUDA
- **性能瓶颈分析**：在 V2 双网架构下，PyTorch 神经网络训练（尤其 CNN 策略-价值双头网络）与高并发自博弈在纯 CPU 或 MPS 上吞吐受限。
- **工程适配要点**：
  1. C11 核心引擎保持零外部依赖，针对 MSVC/MinGW/Windows 补全高精度计时（`QueryPerformanceCounter`）与动态库导出（`gomoku_engine.dll`）。
  2. 训练管线引入 CUDA AMP 混合精度训练与 Windows 多进程并行对弈，通过 SSH 隧道与增量同步脚本实现 Mac 开发、Win4070 训练的工作流分离。
- **实测收益**：迁移至 RTX 4070 后，V2+Rapfi 第 6 轮训练阶段（`train_sec`）缩短至 **71.0 秒**，同时成功推动模型持续晋级（`NNUE val_mse = 0.29994` PROMOTED，`CNN val_top1 = 0.529` PROMOTED，`vs_heuristic = 62.5%`，`vs_v1 = 62.5%`）。

## 2. 为什么需要外教（Rapfi 蒸馏）？只靠本地自博弈有什么局限？

- **核心疑惑**：只让模型在本地左右互搏迭代，会不会陷入“井底之蛙”式的局部最优？
- **原因解析**：
  1. **同质化回音壁**：早期模型对禁手边界、复杂 VCF（连续冲四）和跳三/双活三反制认知不足，纯自博弈容易在低水平稳态中互相迁就，出现“双方都看不见的盲区”。
  2. **冷启动样本稀疏**：弱棋力下很难自然走出高质量防守与长链算杀局面。
- **解决方案（接入 Rapfi 250615 作为外教）**：
  - 通过 Gomocup 协议桥接轻量级强力引擎 Rapfi（`pbrain-rapfi-windows-avxvnni.exe`），在严格时间/节点预算下进行陪练对局与错题蒸馏，并建立独立的 `vs_rapfi` 评估基准（第 6 轮对弈中虽暂为 `0/20`，但提供了真实强敌压迫与高质量高价值局面样本，用于打破自博弈闭环）。

## 3. 核心原理 FAQ：四条线 vs 八个方向？

- **疑惑**：棋盘上每个交叉点明明有上下左右和斜向共 8 个射线方向，为什么代码和论文里总说“看 4 个方向”？斜向难道不看吗？
- **解答**：
  1. **4 条轴线等价于 8 条射线**：过点 $c=(r,\text{col})$ 只有 4 条直线轴——水平 `H (0,1)`、垂直 `V (1,0)`、主对角线 `D (1,1)`、反对角线 `A (1,-1)`（斜向两条全覆盖）。
  2. **双向窗口（9 格编码）**：对每条轴向前后各延伸最多 4 格（连同中心格共 9 格，边界处自动截断为实际长度 $L+1+R$），因此 **4 条线 $\times$ 正反双向 = 完整覆盖全部 8 个射线方向，无一遗漏**。
  3. **对称压缩（镜像归一化）**：同一条直线上“左 $L$ 格、右 $R$ 格”与翻转后的“左 $R$ 格、右 $L$ 格”棋型对称等价。对 $0 \le L,R \le 4$、三进制状态数 $\sum_{L=0}^{4}\sum_{R=0}^{4} 3^{L+1+R} = 43923$ 做字典序镜像折叠后，规范棋型 ID 总数精确压缩为 **`N_CANON = 22143`**（含回文对称型 $363$ 种），大幅减少参数量与查表缓存占用。
  4. **如何形成二维交叉感知**：单条线只能看“一维连珠”，将 4 个方向的嵌入向量在中心格求和后经过偏置与 `ReLU` 非线性激活（$\text{cell\_feat}[c] = \text{ReLU}(\sum_{d=0}^{3}\text{emb}[\text{pat}[c][d]] + b_{\text{cell}})$），**“某方向是活三 + 另一方向也是活三”才跨越阈值被激活**，从而自然捕捉四三、双活三、交叉防守等二维组合棋型。

## 4. 核心原理 FAQ：单网多头 vs 拆分成多个独立神经网络 vs 纯无搜索端到端？

### 4.1 V3 把估值也交给神经网络了吗？
- **是的，而且是价值头与策略头协同训练，但保留搜索**。
- 在 V2 中，`NnueNet` 只有 32 维人工计数特征，本质仍依赖手工规则提特征；`PolicyValueCNN` 虽然端到端但太重，只能在根节点算一次。
- 在 V3 `Pattern-NNUE`（`GPN1`）中，**人工启发式不再主导叶子节点评估**：整张棋盘的棋型特征由共享 Embedding 表与轻量增量累加器（`PnnueAcc`）提取，同时驱动：
  - **策略头（Policy Head）**：为候选着法排序（替代静态打分排序，使 Alpha-Beta 剪枝与 LMR 更准）；
  - **价值头（Value Head）**：直接在搜索树叶节点输出局面胜率估值（`[-1, 1]` 映射为整型分值）。

### 4.2 为什么最终不“完全去掉搜索”，只用一个纯神经网络下棋？
- 五子棋存在极强局部组合爆炸与刚性战术算杀（如 5 步以上的连续冲四 VCF、微妙的先手交换与禁手陷阱）。
- 纯神经网络单步前向（Zero-Search）的并行计算深度固定，在面对“只差一着即成五/防死”的长链精确算杀时极易产生幻觉；而 **NNUE + Alpha-Beta 搜索** 让网络负责直觉（静态局面好坏与先看哪几步），让搜索树负责精确推演（把关键变化展开 6~12 层验证到底），是目前算力下性价比与棋力上限最高的范式。

### 4.3 一个大模型多头共用 vs 拆分多个独立小网络配合，怎么选？
| 方案 | 特征复用 | 增量维护成本 | 搜索叶子可用性 | 工程取舍 |
| :--- | :--- | :--- | :--- | :--- |
| **V2 双网拆分**（轻量 MLP + 重型 CNN） | 低（各算各的特征） | 中（CNN 不支持增量） | 仅 MLP 可进叶子，CNN 仅根节点 | 训练维护两套格式，强模型（CNN）进不了深搜内部 |
| **多独立小网串联** | 低（价值网与策略网各自读盘） | 高（每步落子需维护多套状态） | 耗时成倍叠加 | 内存带宽翻倍，同一棋型信息重复计算 |
| **V3 单网多头共享**（Pattern-NNUE `GPN1`） | **极高**（共享 22143 词表与细胞交互特征） | **极低**（落子仅更新最多 33 个受影响 `(cell, dir)`） | **全树共享**（叶子估值 + 内节点策略排序同一套累加器） | 最优解：训练一体化、增量零重复计算、深度搜索与神经网络深度融合 |

- **结论**：将局面表征统一下沉到单一共享骨干（Pattern-NNUE Accumulator），再分化出轻量的 **Value Head** 与 **Policy Head**，既消除了多网络重复提特征的开销，又让深层搜索树上的每一个节点都能用上端到端学到的局部+全局棋感。

## 5. 为什么训练没有跑满 GPU？及 V3 推进预算规划

### 5.1 实测现象与瓶颈拆解（Win4070 V2+Rapfi 第 6~7 轮）
在 Windows RTX 4070 Laptop（8 GB 显存）跑 V2+Rapfi 时，`nvidia-smi` 实测 GPU 占用约 **41%**、显存 **2064 / 8188 MiB**、功耗 **23.83 W**。原因并非 GPU 没用上，而是**整轮任务 90% 以上时间都在跑 CPU 棋局搜索与评测**：
- **第 6 轮实测总耗时 715.5s**：
  - Rapfi 陪练采样 120 局：**96.3s**（纯 CPU，8 进程 Rapfi）
  - C11 多进程自博弈 480 局：**479.9s**（纯 CPU，16 进程 Alpha-Beta 搜索）
  - 门控与阶梯竞技场评测：**164.1s**（纯 CPU，16 进程对弈）
  - **PyTorch GPU 训练仅耗时 71.0s**（第 7 轮进一步降到 **65.9s**），已比此前 Mac 第 5 轮的 **969.7s** 提速约 **14 倍**。
- 此外，V2 训练阶段的 `NNUE (32->128->64->1)` 和 `CNN (48ch x 4blocks)` 模型本身参数量较小，`BatchSize=512` 下 Python 数据增强与 Host-to-Device 传输占比更高，GPU 算子瞬时就会算完，很难长时间把 4070 的核心打满到 95%+。
- 因此，V3 训练脚本 `training/train_pnnue.py` 将默认 `BatchSize` 提升至 **`2048`**，并训练统一的 **`22143 x 64` Pattern-NNUE** 网络，进一步提高单卡吞吐。

## 6. V3 落地排障实录：绝对色编码下的价值头符号对齐与搜索平衡

在 Win4070 实机跑通 V3 后，我们经历了两次极具工程代表性的排障（也是五子棋 NNUE 实现中最容易踩坑的两个问题）：

1. **搜索排序、LMR 保护与 PVS 根节点复核**：
   - 初版 V3 仅使用未收敛的策略 `logit` 做移动排序并激进应用 LMR（`depth >= 3 && i >= 4`），同时在前 16 步带温度采样且缺少 PVS fail-low 复核，导致自博弈局均仅 `11.6` 步、`vs_heuristic (depth=5)` 只有 `34.4%`。
   - 将局部战术启发式 `eval_move_heuristic / 2` 融回排序、对高战术分着法（`>= 4000`）免疫 LMR、补齐根节点 PVS 精确窗口复核并把叶子估值尺度从 `±25000` 调整为 `val * 22000 + lin_score / 2` 后，自博弈恢复至 `25～28` 步/局，同权重 A/B 实测 `vs_heuristic(d5)` 跃升至 **`62.5% (20-12)`**。
2. **绝对色棋型下的价值头视角翻转 Bug（最隐蔽的根因）**：
   - 尽管搜索修复后旧权重表现提升，但从头预训练的新模型首轮门控仍出现 `16-48 (25%)` 反常回退。排查缓冲样本分布与单步前向预测发现：`PatternNnueNet` 的 22,143 规范棋型采用**绝对黑白颜色编码**（黑=1、白=2），但价值头输出 `tanh(v_raw)` 在白棋回合未对结果取反，导致“黑优局面白棋视角（应为负）”与“白优局面白棋视角（应为正）”在共享 MLP 上梯度互相抵消，网络只学到了固定偏置（黑方约 `+0.5`、白方约 `-0.5`）。
   - 在 [pnnue.c](file:///Users/strongintheearth/CLionProjects/C-Cpp-2026/课程设计/gomoku_ai/src/pnnue.c#L321-L322) 与 [pnnue_model.py](file:///Users/strongintheearth/CLionProjects/C-Cpp-2026/课程设计/gomoku_ai/training/pnnue_model.py#L190-L191) 中对白棋回合（`p_idx == 1`）输出乘以 `-1`（保持 `GPN1` 二进制格式零改动）后，预训练 `val_mse` 立刻从 `0.3245` 降至 `0.2934`，首轮门控一举反转为 **`46-18 (71.9%) PROMOTED`**。
