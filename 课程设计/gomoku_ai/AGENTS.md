# 五子棋大作业项目统一规范

本文件是本仓库中所有后续开发与辅导对话的入口规则。新对话开始处理本项目时，应先阅读本文件，再按需阅读 `docs/` 下的相关文档。

## 1. 项目目标

完成一个可独立运行、遵守五子棋规则、能够完整下完一盘棋的本地程序。这是老师给出的唯一硬性目标。估值、Minimax 和 Alpha-Beta 是适合作为学习与棋力起点的推荐基线，不是及格门槛；老师明确鼓励探索。项目仍应优先建立稳定可玩的版本，再根据投入提高棋力。

## 2. 事实来源与优先级

信息冲突时，按以下顺序判断：

1. 老师或比赛方发布的正式规则与提交要求。
2. `docs/REQUIREMENTS.md` 中标记为“已确认”的需求。
3. `docs/DECISIONS.md` 中最新且状态为“已采纳”的决策。
4. 其他文档和对话中的建议。

不得把猜测写成已确认事实。无法确认的内容必须标记为“待确认”，并写明当前采用的临时假设及其影响。

## 3. 每次对话的工作流程

1. 先阅读本文件；复杂任务再阅读需求、决策、路线图和进度文件。
2. 区分当前请求属于“讲解辅导”“诊断问题”还是“直接实现”。
3. 大型或复杂任务开始前，先确认目标、范围、限制、验收方式和用户希望自己完成的部分；用户已明确授权时可直接执行。
4. 修改前检查现有文件和 Git 状态，不覆盖与本次任务无关的用户改动。
5. 完成后执行与风险相称的编译、测试或规则检查。
6. 对独立、可解释、已验证的增量提交 Git；若远程仓库可用则推送。实验失败但值得记录的过程可以单独提交，不得用未验证的大批文件冒充迭代过程。
7. 对话结束前，把已完成工作、验证结果、风险、未决问题和下一步写入 `docs/PROGRESS.md`；若产生长期决策，同时更新 `docs/DECISIONS.md`。

## 4. 代码归属与教学方式

- 程序主体应由用户完成。助手主要负责解释概念、拆分任务、提供小型示例、审查代码、定位错误和设计测试。
- 用户学习新主题时，先讲清模型和必要语法，再给出可独立完成的小步骤；不要直接倾倒完整作业代码。
- 用户明确要求完整实现或紧急修复时，可以给代码，但在交付后必须解释关键语法、算法和可自行重写的部分。
- 每次只推进一个可以编译、运行和验证的小里程碑，避免长期保留无法运行的半成品。

## 5. 工程规范

- 暂定使用 C++17、CMake 和跨平台标准库实现，保证 CLion 在 macOS 与 Windows 上均可构建；语言标准可在确认电脑编译器后调整。
- 程序结构必须分离棋盘、规则、估值、搜索、计时、输入输出和测试；禁止把主要逻辑堆在 `main()` 中。
- 规则参数应集中管理，棋盘尺寸、搜索时间、胜负判定和禁手开关不得散落为魔法数字。
- 引擎必须优先保证合法落子、正确判胜和正确禁手；棋力提升不得牺牲稳定性。
- 每步限时 60 秒，搜索应预留输入输出和机器波动余量；最终安全余量需用实测确定。
- 正式对局运行时应离线，不依赖网络或外部 API。外部 AI、API 或联网资源只能用于开发和训练阶段，且需记录来源与许可证。
- 使用第三方库或参考开源代码前，确认许可证、课程学术规范和运行时依赖，并写入决策记录。
- 固定随机种子时应可复现；不得依赖未定义行为、偶然的未初始化内存或平台特有扩展。
- 代码标识符使用英文，说明性文档使用中文。代码注释解释“为什么”，不重复显而易见的语句。
- 老师要求制作和调试过程在 GitHub 仓库中可见，并建议复用现有 C++ 课程仓库。本地开发、提交和推送流程以 `docs/GIT_WORKFLOW.md` 为准。
- 不提交密码、令牌、个人私密数据、编辑器缓存或构建产物；构建目录和本机配置必须由 `.gitignore` 排除。

## 6. 验证规范

最低验证范围包括：

- 编译无错误，并在用户实际使用的 Windows/macOS 环境中运行。
- 合法落子、越界、重复落子、胜负判定、和棋及禁手测试。
- 固定局面的战术回归测试。
- 自动对弈不崩溃、不超时，并保存可复盘的棋谱和日志。
- 修改搜索或估值后，用固定测试集和自对弈比较，而不是只凭个别棋局判断强弱。
- 每次准备提交时检查 `git diff` 和 `git status`，只暂存本次需要展示的文件；推送后确认本地与远程状态一致。

## 7. 当前关键上下文

- 用户是 C/C++ 初学者，已初步接触结构体、指针和递归，未系统学习树、Minimax、Alpha-Beta、哈希表和神经网络。
- 老师唯一的硬性目标是程序能够完成一盘五子棋对战，并鼓励自主探索。

- 制作和调试过程必须在老师的 GitHub 课程仓库中可见，小版本也可以提交。
