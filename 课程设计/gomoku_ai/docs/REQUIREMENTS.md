# 需求与规则基线

状态说明：

- **已确认**：用户或老师明确给出。
- **临时假设**：为了前期设计暂按此执行，确认后可修改。
- **待确认**：会影响实现，必须向老师、平台或用户确认。

## 1. 已确认需求

### 1.1 棋局规则

- 棋盘为 15×15。
- 黑方先行。
- 每步最多 60 秒，无总时限。
- 存在禁手。
- 最终程序需要完整、可运行。

### 1.2 技术限制

- 使用 C 或 C++，开发环境为 CLion。
- 可以使用第三方库。
- 可以查询和参考开源代码。
- 正式运行在本地，不要求联网。
- 老师唯一的硬性目标：提交的程序能够完成一盘五子棋对战。
- 估值算法、Minimax 和 Alpha-Beta 是推荐的基础保底方案，不是强制及格条件。
- 老师完全鼓励探索，棋力、搜索优化、神经网络等均可作为自主方向。

### 1.3 GitHub 过程要求

- 制作、调试和迭代过程必须在 GitHub 老师可见的课程仓库中留下记录。
- 优先直接复用目前的 C++ 课程仓库，不另起一个与课程脱节的仓库。
- 每个细小但有意义的版本都可以提交和推送，包括棋盘的图形界面等局部改进。
- 提交记录应反映真实开发过程，而不是最后一次性上传全部文件。
- 已定位课程仓库 `Zt66666cpu/C-Cpp-2026`，本项目目录为 `课程设计/gomoku_ai/`。
- 后续提交只暂存本项目的文件，不混入课程仓库中其他作业尚未提交的改动。

### 1.4 人员分工

- 程序主体由用户完成。
- 助手用于讲解、检查、调试、测试设计和必要时的局部帮助。

## 2. 临时假设

以下假设仅用于开始设计，不是最终比赛规则：

1. 棋局为有禁手五子棋；黑方不得形成长连、双四或双三，白方不承担相同禁手。
2. 黑方只有恰好五连获胜，白方五连或更长连续棋子获胜。该项需按连珠规则再核实。
3. 满盘且双方均无五连时判和。
4. 第一版采用命令行文字棋盘和坐标输入，规则引擎与界面分离，之后可增加图形界面。
5. 语言先采用 C++17；它可在 CLion 常见 Clang/GCC/MinGW 环境中使用，也能用接近 C 的写法逐步学习。
6. 搜索预算暂按 55 秒设计，为落子计算、输入输出和系统波动保留余量；最终值以实测为准。
7. 正式对局设备 CPU 架构尚不确定，因此第一版优先纯 CPU、单机、离线运行。

## 3. 待确认问题

### P0：开始判禁手前必须确认

- “有禁手”是否严格等同连珠（Renju）规则？
- 黑方禁手是否包含长连、双四、双三三类？
- 双三中的“活三”采用哪种定义？
- 是否需要处理完整连珠开局规则、开局交换规则或三手交换？
- 白方形成长连时是获胜还是和棋？

### P1：程序结构确定前需要确认

- 提交方式是直接运行交互程序，还是评测平台通过标准输入输出调用？
- 输入坐标格式、非法输入处理、退出方式是否有规定？
- 是否需要图形界面或只要求命令行？
- 必须提交源代码、可执行文件还是实验报告？
- 老师如何判定“实现了”估值、Minimax 和 Alpha-Beta？是否需要保留可视化搜索过程或报告？
- 第三方库和开源代码是否允许直接链接、修改，报告是否需要声明来源？

### P1：开发环境确认

- CLion 当前使用的编译器名称和版本是什么？
- 最终演示电脑是 macOS 还是 Windows？
- Windows 电脑使用 MSVC、MinGW 还是 WSL 编译？

## 4. 不可牺牲的验收条件

- 任何输入和历史局面下都不产生非法落子。
- 胜负与禁手判定有独立测试。
- 每次搜索不超过界面约定时间。
- 搜索崩溃、提前返回和超时时都有明确处理方式。
- 程序从空棋盘开始可以完整下完一局。
- 最终 GitHub 仓库包含可追溯、真实的小步开发记录。
- 若使用估值、Minimax 和 Alpha-Beta，代码中能找到对应实现和调用链；这是推荐基线，不作为唯一合格方式。
