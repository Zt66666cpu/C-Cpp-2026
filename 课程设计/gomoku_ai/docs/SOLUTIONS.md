# 前期技术方案比较

项目位于课程仓库 `C-Cpp-2026` 的 `课程设计/gomoku_ai/` 目录。

## 1. 共同基础

无论选择哪套棋力路线，都必须先完成相同的稳定内核：

1. 棋盘表示与合法落子。
2. 五连、长连、和棋判定。
3. 黑方禁手判定。
4. 每步计时与保底合法落子。
5. 至少一种能够完成整盘对局的自动落子策略；推荐先实现估值、Minimax、Alpha-Beta 作为学习基线。
6. 固定局面测试、自对弈和可复盘棋谱。

三套方案的区别在“如何评估局面”和“如何选择搜索分支”，不是跳过基础工程。

## 2. 方案 A：经典搜索强化路线

### 核心思路

使用手工棋型估值驱动 Alpha-Beta，并通过候选点筛选、迭代加深、置换表、杀手着法和必胜威胁搜索提高棋力。神经网络不进入第一版。

### 主要组成

- 棋盘特征：连子长度、开放端、活三、冲四、活四、双威胁等。
- 估值：根据当前行棋方、棋子位置和棋型赋分，并保持攻防对称。
- Minimax + Alpha-Beta：递归实现，不显式建立整棵搜索树。
- 候选着法：只搜索已有棋子周围、有战术价值的点。
- 增强项：迭代加深、Zobrist 哈希与置换表、历史/杀手着法、静态搜索、VCF/冲四胜搜索。

### 优点

- 与推荐基础方案一致，每一步都能在答辩中解释。
- 纯 CPU、本地、离线即可运行，不依赖训练数据和框架。
- 可控性和可调试性最好，遇到问题能按规则、估值、搜索逐层定位。
- 在 60 秒相对充足的条件下，做好棋型估值和威胁搜索已有较强竞争力。

### 代价与风险

- 需要学习递归搜索、剪枝和哈希表，但这些可以按里程碑逐步加入。
- 棋型估值需要大量测试与调参，代码“能下”与“下得好”之间有距离。
- 双三禁手与搜索中的威胁识别相互影响，规则模块必须可靠。

### 适合结论

最适合作为主线。它保证课程底线，失败风险最低，并有清晰的后续优化空间。

## 3. 方案 B：神经网络估值/着法引导路线

### 核心思路

在 RTX 4070 笔记本上训练策略网络和价值网络，再让 C++ 程序离线加载模型。网络可以只负责给候选着法排序或评估局面，最终仍由 Alpha-Beta 完成搜索，从而同时满足课程和棋力目标。

### 主要组成

- 用 Python/PyTorch 在 Windows 4070 上训练。
- 数据来源可选：自对弈、公开棋谱、教师许可的开源数据；外部 AI 或 API 只能辅助生成或标注数据。
- 网络输入为棋盘状态，输出落子概率和局面胜率。
- 训练后导出 ONNX 或通过 LibTorch 集成到 C++；正式运行全部在本地。
- 搜索侧使用网络筛选候选着法或替代部分手工估值。

### 优点

- 上限最高，能学到不易手写的局面直觉。
- 4070 可显著缩短训练等待时间。
- 若只把网络作为候选排序器，原 Alpha-Beta 基线仍然保留，完成风险较可控。

### 代价与风险

- 新增 Python、PyTorch、数据处理、训练评估和模型部署一整套技能。
- 自对弈数据质量和数量决定效果，训练不足时可能弱于手工估值。
- C++ 推理库、模型格式和 Windows/macOS 部署会增加构建复杂度。
- 禁手规则必须在生成数据、训练标注和运行搜索三个阶段保持一致。
- 用户目前只对神经网络有初步认知，不建议把能否完成整盘对局押在这条路线。

### 适合结论

适合作为方案 A 完成后的增强项。若时间不足，保留 Alpha-Beta 版本；若时间充足，先做“小型策略网络只负责着法排序”，不要一开始直接做完整 AlphaZero。

## 4. 方案 C：启发式蒙特卡洛树搜索路线

### 核心思路

使用 UCT/MCTS，通过大量模拟对局估计每个候选点的价值，在 60 秒内不断扩展搜索树。加入必胜/必防棋型检测和领域裁剪，避免纯随机模拟在五子棋中效率过低。

### 主要组成

- 选点、扩展、模拟、回传四步循环。
- 节点统计胜率、访问次数和先验分数。
- 用棋型启发式限制候选并引导模拟。
- 战术层先检查立即获胜、立即防守、冲四和活三；MCTS 负责复杂局面选择。
- 可逐步加入并行搜索。

### 优点

- 天然支持任意时间搜索，到点即可返回当前最佳着法。
- 较少依赖精细手工估值，扩展思路与 Alpha-Beta 明显不同。
- 适合并行化，未来可与神经网络策略结合。

### 代价与风险

- 五子棋胜负稀疏，随机模拟常无法及时发现细长威胁，纯 MCTS 通常弱于成熟 Alpha-Beta。
- 需要可靠启发式和战术模块，实际难度不比 Alpha-Beta 小。
- 若为了学习与安全基线保留 Alpha-Beta，就必须维护两套搜索系统，规模会增大。
- 对初学者而言，调试“为什么某次模拟导致选择变化”比调试确定性的剪枝更困难。

### 适合结论

适合作为有充足时间后的对照实验或扩展模块，不建议作为唯一主引擎。

## 5. 比较

| 维度 | A 经典搜索强化 | B 神经网络引导 | C 启发式 MCTS |
|---|---|---|---|
| 与推荐基础方案契合度 | 很高 | 中，可保留 Alpha-Beta | 中，可另做 Alpha-Beta |
| 初学阶段所需额外知识 | 中等 | 高 | 中高 |
| 纯 CPU 运行 | 适合 | 适合，但依赖模型推理 | 适合 |
| RTX 4070 利用率 | 不需要 | 高 | 非必需 |
| 调试与答辩可解释性 | 高 | 中 | 中低 |
| 完成风险 | 低到中 | 高 | 高 |
| 潜在棋力上限 | 高 | 很高 | 中高 |
| 建议优先级 | 主线 | 第二阶段增强 | 备选实验 |

## 6. 推荐决策

推荐采用 **A 作为首选实现主线，B 为完成可玩版本与基准测试后的可选增强，C 仅在仍有充足时间时做实验分支**。老师不强制使用三个基础算法，但 A 最适合当前知识基础和有限投入。

具体顺序：

1. 规则引擎和测试先完成，确保任何引擎都不会因禁手或胜负错误直接输棋。
2. 先实现能合法完成整盘对局的基础策略；推荐继续实现估值、Minimax 和 Alpha-Beta 作为理解搜索的里程碑。
3. 加入候选裁剪、迭代加深和着法排序，以较少代码获得第一轮棋力提升。
4. 加入置换表、威胁搜索等高级搜索技术，持续用固定测试集验证。
5. 只有在以上工作稳定后，再决定是否训练小型神经网络。

该顺序的原因是：人力有限时，前四步已经直接提升对局表现；神经网络带来高上限，也同时引入数据、训练、部署和跨平台风险。先完成一个可完整对弈的版本，并逐步按 A 增强，能保证始终有一个可提交版本。

## 7. 需要用户评估的决策点

- 是否接受 A 作为主线，而不是三套同时开发。
- 是否把 B 定位为“网络辅助 Alpha-Beta”，而不是从零实现完整 AlphaZero。
- 是否接受第一版使用命令行界面，图形界面放到规则和引擎稳定之后。
- 是否愿意按“每完成一个小模块就测试”的节奏学习，而不是先写完整程序再统一调试。
